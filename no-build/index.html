No-build:
pipe dream, or near future?

by Lea Verou lea.verou.me • lea＠verou.me
## Dependencies in JS ```js import { marked } from 'marked'; const md = '# _Hello_ Markdown!'; const html = marked.parse(md); console.log(html); ```
Suppose we want to include a library to do something nontrivial, e.g. parse Markdown. We find a library we like and want to use it in our project. How do we make it work?
## Dependencies in Node.js ```bash $ npm install marked ```
In Node.js and other JS runtimes, things are simple. We install the library with `npm install` and things Just Work™.
## Dependencies in the browser ```error Uncaught TypeError: Failed to resolve module specifier "marked". Relative references must start with either "/", "./", or "../". ```
Now suppose we need to use a library client-side. We try to `npm install` again, but nope, that doesn’t work. You need to use a bundler! Suddenly, the workflow is 10x more complex.
## Now you have multiple problems - Which bundler?? Vite, Webpack, esbuild, Rollup, Parcel... - Configuration - Source != Distribution - Compilation → Sourcemaps - Entry point
Now you have multiple problems. If you’re using a meta-framework like Next.js or Nuxt, they already encapsulate this choice for you, but otherwise you need to pick one. And then install it. And then configure it. And then run it. And remember to run it whenever you want to change anything. Now you need to have a lot more: - a source directory separate from a served directory - an entry point concept - a compile step between saving and reloading - an artifact that isn't the file you wrote - sourcemaps, to undo the previous line This introduces more complexity to solve problems the bundler introduced: - Sourcemaps - Hot reloading - Code splitting / chunking
## Dependencies across ecosystems | | How to use a dependency | |-----------|----------------------| | Node.js | `npm install marked` | | Rust | `cargo add marked` | | Python | `pip install marked` | | Web | `npm install marked` + 🤕🤕🫠 |
One of these is not like the others. In NodeJS, you just npm install and reference specifiers straight away in your code. Same in Python, with pip install. Same in Rust with cargo add. In healthy ecosystems you don’t ponder how or whether to use dependencies. The ecosystem assumes dependencies are normal, cheap, and first-class. You just install them, use them, and move on. “Dependency-free” is not a badge of honor.
## In healthy ecosystems dependencies are normal, cheap, and first-class. “Dependency-free” is not a badge of honor.
## The web platform has outsourced the most fundamental ecosystem functionality to third-party tooling.
Abstraction is the cornerstone of modern software engineering. Reusing logic and building higher-level solutions from lower-level building blocks is what makes all the technological wonders around us possible. Imagine if every time anyone wrote a calculator they also had to reinvent floating-point arithmetic and string encoding!

Why do we use bundlers?

  1. Transpilation TS, JSX, CSS preprocessors, templating, etc
  2. Performance bundling, minification, etc
  3. Dependency resolution Making `import "foo"` work in the browser

One of these is not like the others

Do you notice that one of these is not like the others? Performance and transpilation are generally _advanced concerns_. You can get quite far without hitting them, especially in an SPA. But using a dependency is not an advanced use case, it’s something you usually need very early on. Even in a one-off experiment or a CodePen snippet you need dependencies!

Delightful APIs

Incremental user effort produces incremental value

Good user interfaces make simple things easy, complex things possible, and ensure a smooth transition from simple use cases to more complex ones.
When a small increase in use case complexity results in disproportionate increase in UI complexity, this is called a _usability cliff_ and it is an **antipattern**. The way dependencies work in the web platform is a textbook usability cliff. There is nothing wrong with bundlers when used as a performance optimization to minimize waterfall effects and overhead from too many HTTP requests. You know, what a bundler is named after! Or to provide a different DX, possibly optimized for specific use cases. **It is okay to require advanced tools for advanced needs**, and performance optimization is generally an advanced use case. Same for most other things bundlers and build tools are used for, such as strong typing, linting, or transpiling. All of these are needs that come much later than dependency management, both in a programmer’s learning journey, as well as in a project’s development lifecycle.
Tons of languages are compiled, what's the problem?
Oftentimes when discussing these issues, I get the question “but other languages are completely compiled, why is it a problem here?”. Yes, but their compiler is official and always there. You literally can’t use the language without it. You don’t get a broken experience, you get _no experience at all_.

Fragmentation is the problem

The problem is not compilation, it’s fragmentation. It’s the experience of linking to a package via a browser import only to see errors about specifiers. It’s the visible complexity and indirection just to use a utility function.
There is no coherent story. Web platform primitives that work fine in the browser, may or may not work in certain bundlers and you can’t know until you test in all of them. **Instead of the bundler serving our code, our code has to adapt to appease the bundler.** 

import { BaseElement } from "./base.js";
import style from "./style.css" with { type: "css" }

class MyElement extends BaseElement {
	static const style = style;
	// ...
}
It gets worse. In some cases the web platform _itself_ must adapt to appease bundlers. So much collective effort invested in fixing problems that would not exist if bundlers weren't so necessary.

## Specifiers
```js { .bad } import { marked } from '/node_modules/marked/lib/marked.esm.js'; ``` ```js { .bad } import { marked } from '/lib/marked/lib/marked.esm.js'; ``` ```js { .bad .span-2 } import { marked } from 'https://esm.sh/marked@18.0.13/lib/marked.esm.js'; ``` ```js { .ok } import { marked } from 'https://esm.sh/marked'; ``` ```js { .good } import { marked } from 'marked' ```
The first requirement is specifiers. Specifiers are an _abstraction_. They decouple the dependency from its version, file structure. Packages can be upgraded, or change the mapping of exports to file paths without requiring any downstream changes. Multiple versions of the same package can co-exist, and specifiers just resolve to the correct one. These are not consumer concerns, and should not be scattered all over the codebase. Some CDNs do allow URLs that map to specifiers, providing the same encapsulation. However, even that way, version management is still ad hoc.

1
Rawdogging node_modules/ imports

```diff - import { marked } from 'marked'; + import { marked } from '/node_modules/marked/lib/marked.esm.js'; ```

The Good It works! 🎉

…for this particular case

The Bad Requires deploying node_modules/

Wasteful and insecure. Most hosts do not even deploy `node_modules/` by default. Now you need additional ad hoc tooling to make this work in prod.

The Bad We just lost the abstraction of specifiers

Have you wondered why we use specifiers and not URLs? Specifiers are an _abstraction_ over URLs. They decouple the actual file structure from the dependency.

The Ugly Breaks with transitive dependencies

```js import {html, css, LitElement} from '/node_modules/lit/index.js'; ``` ```error { .delayed } Uncaught (in promise) TypeError: Failed to resolve module specifier "@lit/reactive-element". Relative references must start with either "/", "./", or "../". ```
But the real dealbreaker is that even if you stomach all other warts, this only works for dependencies that don’t use dependencies. Once a dependency has its own dependencies, this approach breaks down completely.

2
Import from CDNs

```js import {html, css, LitElement} from 'https://esm.sh/lit'; ``` - Transitive dependencies work - Specifiers, not paths (mostly) { .check-list .green .text .delayed-children }

A point of failure you don’t control

It is always a bad idea to introduce a dependency on a whole other domain you do not control, and an even worse one when linking to executable code. Any third-party domain is an unnecessary additional point of failure you do not control. I still remember scrambling to change JSDelivr URLs to Unpkg during an outage right before one of my talks, or having to hunt down all my repos that used RawGit URLs when it sunset, including many libraries. Wanted to code on a flight? Good luck. Needed to show a live demo during a talk, over clogged conference wifi? Maybe sacrifice a goat to the gods first. More complexity: - How to avoid CDN roundtrips for local dev? - Proxies for APIs that require COEP/single-origin isolation.
## Inconsistency
Because everything is URLs, nothing prevents the same module from being referenced in multiple ways (different versions, from different CDNs, etc), leading to potential inconsistencies and even bugs.

The Bad What about local packages?

If a CDN is both your package manager and your source of executable code, how do you modularize _your own_ code?

The Ugly Security implications

Unless you link to a specific version, down to the patch number and/or use SRI, the resource could turn malicious overnight under your nose if the package is compromised. And even if you link to a specific version, there is always the risk that the CDN itself could get compromised. Who remembers polyfill.io?

3
Import maps

```html <script type="importmap"> { "imports": { "marked": "https://esm.sh/marked@18.0.13", "localpkg": "../localpkg/index.js" } } </script> ``` ```js import { marked } from 'marked'; import stuff from 'localpkg'; ```
- Transitive dependencies work - Specifiers! - Centralized dependency management - Local packages { .check-list .green .text .delayed-children }
